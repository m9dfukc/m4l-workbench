## 1. "Dials are larger and text sharper in the mock-up; Live feels cramped"

**Diagnosis — confirmed, but the cause is the box height, not the track colour.**

- `live.dial` has a fixed height. With `showname 0, shownumber 1` it is **36 px** whatever the saved
  rect says: all 332 such dial rects in the Max and Live installations are 36–37 px high; name + number =
  47–54, neither = 27–28 [measured: scan of 869 `.amxd/.maxpat/.maxhelp` files under Max.app and
  Live's App-Resources, box heights grouped by `appearance/showname/shownumber`].
- The shell saves the pointer dials as 40 × 45 and the page dials as 34 × 40 / 36 × 36. In Live the
  painter gets h ≈ 36 for all of them: Write Pitch (rect 66 22 40 45) draws its ring at x 77–97,
  y 24–41 and its value on rows 49–55; the painter formulas give exactly that for h = 36 (knob 25,
  r 8.5, baseline y+33.5) and a ring down to y 49 with the value on rows 58–64 for h = 45. LFO Rate (646 83 34 40): ring
  x 654–673, value rows 111–116, again h ≈ 36 [measured: shot `lfo-env`; inferred, `mgraphics.size`
  not read in Max → [open]].
- Result: ring outer diameter **20 px in Live vs 28.5 px in the mock-up/preview** (70 %), and 10 px
  of dead space under every pointer dial. The canvas preview and the mock-up use the saved 45 px,
  which is why they looked right.
- Track ring: #6e6e6e on the #989898 panel = grey 110 vs 152, contrast 1.77 : 1; dark #5c5c5c on
  #424242 = 1.50 : 1 [measured: shot, column x 126; contrast computed]. Visible but weak; it makes
  the small ring look even smaller at low values. Claude's first guess is therefore half right.
- Sharpness: Live's own labels and the painted text have the same grey-scale anti-aliasing at 1×
  (darkest glyph pixels 17–38 in both) [measured: shot]. The mock-up was sharper because a browser
  on a HiDPI screen draws 2 device pixels per pixel. At 1× an 8-px font has a 4-px x-height; nothing
  renders that crisply. What can be done: larger type, whole-pixel positions, no fractional sizes.
- "Cramped" in numbers: label → ring gap 2–3 px; Gate/Resync labels 0 px above their tabs (§8);
  matrix headers 7.5 pt; panel padding 6 px while the text is inset 10 px.

**Proposal (one recommendation, no real alternative):**

1. Save every dial with its true height **36** and let the painter fill it: `r = min(w/2 − 3.5,
   (h − 10)/2)` → **r 13** for all three dial widths (40, 36, 34), `cy = r + 2`, stroke 2.5, needle
   1.5 to 0.71 r, value text 9 px with baseline at `h − 1`, x rounded to whole pixels. The value sits
   in the open end of the 270° arc (arc ends at y 25.4, glyphs start at y 28). Same ring as the
   mock-up, in the box Live really gives. Mock-up: `pointer-rows.html` (three-way comparison).
2. Track colour for dials only: light **#5a5a5a** (2.39 : 1), dark **#747474** (2.15 : 1). Tab and
   pill outlines keep #6e6e6e / #5c5c5c.
3. Type: **9 px** for all labels, values and tab texts (Ableton Sans Medium), titles 9 px Bold caps;
   8 px only for Option C's matrix headers; never 7.5. Painters: `x = Math.round(x)` in `text()`,
   baselines whole numbers: tab/pill/numbox text baseline `(h + 8) >> 1` (h 14 → 11, h 13 → 10,
   h 16 → 12).
4. Spacing rules (4-px grid): label box 13 px high; **dial.y = label.y + 16** (4 px between glyphs
   and ring); a label above a tab/pill: **control.y = label.y + 16**; a label on the same line as a
   painted control: **label.y = control.y − 1** (h 14); a `live.comment` whose text should align with
   a control's left edge: **comment.x = control.x − 2**; 8 px between groups; nothing closer than
   4 px to a panel edge.
5. Fix the preview/mock tooling to draw dials at 36 px so it can be trusted again (§9.1).

[open] A taller dial would need Live to give a taller box. `fontsize` changes the box height
(8 pt → 42, 10 pt → 47–50 with name + number [measured: same scan]), and the painter ignores the
box font, so `fontsize 12–13` might buy 4–6 px. Not needed for the layout below; probe only if the
36-px dial still feels small.

## 3. Global → Transpose does nothing when both pointers are in Sync

Transpose adds semitones to Hz pointers only [code: `aliasing.genexpr` lines 316–317]. Options:

- **A (recommended): two dials, each greyed while it has nothing to act on.** `Transpose` (as now)
  is greyed when no pointer is in Hz; a new `Sync Rate` (enum ÷16 ÷8 ÷4 ÷2 ×1 ×2 ×4 ×8 ×16, default
  ×1, shown "×2") multiplies every synced pointer rate and is greyed when no pointer is in Sync.
  Powers of two keep synced pointers on the grid and keep the write:read ratio, which is what
  Transpose does for Hz pointers. One meaning per parameter (clean automation names), correct in the
  mixed case, +1 parameter. Looks: `global.html`, group "TUNE".
- **B: grey Transpose out when both pointers are in Sync.** No DSP change, honest, 5 minutes in the
  pages script (`activeFor`). Do this in any case until A exists.
- **C: one dial that changes meaning (st in Hz, ×2^k in Sync). Not recommended**: 11 of every 12
  steps would do nothing in Sync, and Live's automation lane would say "Transpose +12 st" for "×2".

## 7. Mod matrix: what can go, and a clearer design

**Diagnosis.** 108 identical bright fields (#dedede, grey 222 on 152) with a centre tick each: the
empty state is the loudest thing on the page; cells are 20 × 12; headers are 7.5-pt abbreviations
("R Frq", "R Fb", "Ctr", "Wid") that touch each other [measured: shot `mod`]. Wavetable's matrix is
destination-based (rows = parameters, columns = sources) and nearly blank until used [sourced:
https://www.ableton.com/en/blog/new-wave-depth-look-wavetable/ — "destination-based"; the row/column
detail and its Matrix | MIDI source tabs are from memory of the instrument, [hypothesis]].

**What can go** (reasons from what each does):

| Candidate | Why | Verdict |
|---|---|---|
| source **Drift** | a slow smooth random, 0.07–0.13 Hz per voice [code: genexpr line 513] = LFO shape Random at ~0.1 Hz with Spread | drop (12 cells) |
| target **Res Fdbk** | changes decay/level of a section that is off by default; ±95 % feedback under audio-rate sources invites blow-ups | drop |
| target **Band Width** | sounds like a weaker Band Center for every source | drop |
| target **Drive** | level-dependent; Output covers dynamics, Env → Drive is a feedback loop | drop |
| source Mod Wheel | Live can map the wheel per Set, but not per preset | keep; second tier if 7 columns are wanted |
| Voice, Neighbour, Read Osc | the device's own character (audio-rate, pitch-locked) | keep; rename the column "Next" |
| Write (gate), Sym, Size, pitches, Spread, Band Center, Res Freq, Output | each audibly distinct | keep |

**Options** (`mod-matrix.html`, A / B / C side by side):

- **A (recommended): destinations as rows, 9 targets × 8 sources = 72 cells, one view.** Removes
  36 parameters: `mx_dr_*` (12) and `mx_<src>_dv`, `_bw`, `_rb` for the 8 remaining sources (24).
  Rows with full names: Write Pitch, Write Sym, Write Gate, Read Pitch, Read Spread, Size, Band
  Center, Res Freq, Output. Columns in three groups: LFO 1, LFO 2, Env | Vel, MW | Voice, Next,
  R Osc. Geometry: header comments (9 pt, centred) x−4 28 36 13 for cell x = **710, 740, 770, 804,
  834, 868, 898, 928**; rows y = **44 + 13·r**; cell 28 × 12; row label comment 648 y−1 60 13; a
  2 × 8 px marker (`panel`) at 646 y+2 in the write accent (rows 1–3), read accent (rows 4–5) or
  45 % label grey.
- **B: keep all 108, two page tabs by target area.** Page tabs LFO · Env | Mod Table | Mod Tone |
  Tone | Global (5 × 63 px); sources stay rows (9), six targets per view: W Pitch, W Sym, W Gate,
  R Pitch, Spread, Size / Drive, Center, Width, Res Freq, Res Fdbk, Output. Cells 41 × 12 at
  x = 700 + 43·c, y = 44 + 13·r; headers x−2 27 45 13; row labels 644 y−1 56 13. No parameter
  change; costs the one-glance overview and a fifth tab.
- **C: today's 9 × 12 grid, repainted only** (cell rule below, headers 8 pt). Cheapest; still 108
  cells of 20 px and abbreviations.

**Cell painter (all options).** Value 0: a quiet slot, fill light **#8c8c8c** / dark **#393939**
(1.17 : 1 and 1.15 : 1 against the panel), radius 2, no tick. Value ≠ 0: field light #dedede / dark
#262626, the depth as text (9 px, baseline y+9, "+35" / "−40") and a 2-px bar from the centre along
the bottom edge (rows h−3 … h−2) in the row's accent over a 1-px hairline. Used cells are then the
only bright things on the page. Colours stay graphite + the one read blue.

## 9. Further issues, ranked

1. **The layout table and the preview do not know Live's fixed `live.dial` height.** `layout.md`,
   `bootstrap_shell.py`, `check_shell.py` and `make_preview.mjs` treat dials as 45/40 px; that is
   how a face that looked right offline came out 30 % smaller in Live. Give the checker a rule
   (dial h = 36 with showname 0) and the preview the same number.
2. **The two `live.meter~` are stock green** on a graphite face; `Palette.meter` exists but nothing
   uses it. Set `coldcolor/warmcolor/hotcolor/overloadcolor` and `bgcolor` from the pages script with
   the panel colours (light #3c3c3c on #dedede, dark #9a9a9a on #262626) [hypothesis: attributes
   from the refpage, behaviour in Live not tested].
3. **The write accent is the text colour** (light #1c1c1c vs #111111, dark #e4e4e4 vs #d2d2d2), so
   only "read" is recognisable as a role; write and neutral bars cannot be told apart in the matrix.
   Either accept two roles (read blue, everything else graphite) and say so, or give write its own
   hue. The row markers in Option A are built for either.
4. Text of left-aligned `live.comment`s starts 4 px right of the controls below them (titles,
   Gate, Retrig) → rule in §1.4.
5. Greyed sections on the light theme (Tone: Drive, Resonator) keep their values at 45 % alpha;
   readable, but the read-blue rings lose their hue almost completely. Fine as "off".
6. The Write and Read panels end 10 px below their last control today; the shape strip uses it.

### b.3 What moves or hides, and how the user reaches it

- **Always visible** (was spread over rows and the Global page): both pointers with shape and
  state, Size, stereo Width, Output, the meter, and the modulation of one target.
- **Modulation**: pick the target in the strip's menu (Write Pitch, Write Sym, Write Gate, Read
  Pitch, Read Spread, Size, Band Center, Res Freq, Output) and set the 8 depths beside it. No page
  change: an LFO page can stay open while its depth is set. Optional later: the strip follows the
  last touched target control, as Granulator's "Auto" [hypothesis].
- **One click away** (side tabs): LFO 1, LFO 2, Env, Band (+ Drive), Res, Limit, Global. The two
  LFOs are no longer visible together; Tone is split in two pages, Global in two.

### b.4 Cost of (b) compared with (a)

- **Display**: 328 × 136 → 496 × 85. Same area, but each of the 5 lanes drops from 22 to 13 px and
  the Tone curve from 157 to 85 px (D31 is undone). The display script needs a new layout and new
  tests. This is the biggest loss; the table is the device's face.
- **Overview of modulation is lost**: (a)'s matrix shows all 72 depths at once; (b) shows 8. Which
  targets are modulated cannot be seen without stepping through the menu. A Live parameter menu
  cannot mark its items at runtime; a marker row (9 dots) would cost the strip's calm [open].
- **Page switches**: 4 pages → 7, with 5–10 controls each. Fewer switches for modulation and
  pointer work, more for Tone (Band/Res) and for comparing the two LFOs.
- **Width**: −168 px in the device chain.
- **Build effort**: (a) changes rects, three painters and two checker rules. (b) regenerates the
  whole shell (every rect, new panels), rewrites the pages rules (7 pages, 72 cells on 8 rects,
  target menu), re-lays the display and its tests, adds a name row to the dial painter and a strip
  box painter, and needs the Sym label (D6: Curve/Skew/Width/…) solved inside a dial box (a comment
  over the name row, or the painter reading a label attribute set by the pages script [open]).
  Roughly three to four times (a).
- **Live parameters**: none beyond the assumptions. +1 stored-only `mod_target`; `page` gets 7
  values; Size changes its object class, not its parameter.
- **Risks in Live** [open]: that a jspainter on a `showname 1` dial gets the full 48 px and Live

### h.4 The one probe before building

Question: what does a jspainter get as `mgraphics.size` on a `live.dial` with `showname 1,
shownumber 1`, and does the saved height matter?

Evidence so far: shipped boxes of that kind are 47–48 px (53–54 at larger fonts) [measured: §1];
today's dials have `shownumber 1` and Live shows only the painter's value, so the painter replaces
the native drawing [measured: t4 screenshots]. Not known: the size the painter sees.

Probe (standalone Max, NonRealTime smoke run, no Live): a test patch in presentation mode with the
dial painter and five dials, and one line added to the painter (once per box):

```js
// in paint(), guarded by a per-box flag
post("dialprobe", varnameOf(), "size", mgraphics.size[0], mgraphics.size[1],
     "rect", box.rect, "pres", attr("presentation_rect"),
     "name", attr("showname"), "number", attr("shownumber"),
     "font", attr("fontsize"), "appearance", attr("appearance"), "\n");
```

| Dial | showname / shownumber | saved rect h | fontsize | Expect |
|---|---|---|---|---|
| `p_a` | 1 / 1 | 48 | 9.5 | size 42 × 47–48 → hybrid as drawn |
| `p_b` | 1 / 1 | 60 | 9.5 | 47–48 again = height is fixed (then save 48) |
